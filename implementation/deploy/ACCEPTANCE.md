## 一、批次 1 · 收得到钱

### A-00 · ★ 四个新模块在 ESM 下能被加载（门槛项）

**为什么排在最前面**：`canvas-api/package.json` **L5** 是 `"type": "module"`，
整个后端是 **ESM**。四个新模块（`credits.js` / `routes-credits.js` / `ldxp-redeem.js` / `ziyu.js`）
只要有一处用了 CommonJS 写法（`require` / `module.exports`），**整个 api 容器会起不来**，
而且报错信息通常只指向第一个文件，容易误判。

**做什么**：在权威树 `canvas-api/` 目录下，用 ESM 方式逐个 import 四个模块。

**期望**：4/4 加载成功，无 `ERR_REQUIRE_ESM` / `ReferenceError: require is not defined`。

**证据**：四条 import 的输出（成功即无输出，失败会抛错——把抛错原文贴上来）。

**不过怎么办**：查该文件顶部有没有残留 `require(` / `module.exports`；
`db.js` 的导出名是 `query` / `getPool` / `migrate` / `closeDb`，import 名字对不上也会炸。

> 本仓桩环境已实测 **4/4 通过**（见 `APPLY.md` §4 E-01），但**桩不等于真机**，这一项仍要在权威树重跑。

### A-02 · Key 注入发生在服务端，前端拿不到

**做什么**：三件事一起看。

1. 浏览器 DevTools → Network，看发往 `/ziyu/...` 的请求头里 `Authorization` 是**什么**。
2. 在页面上执行 `localStorage` / 渠道配置导出，搜索是否出现紫域 Key。
3. 对构建产物搜索：`grep -r "ziyuai" dist/ web/dist/ 2>/dev/null`。

**期望**：

- (1) 浏览器看到的 `Authorization` 要么被 nginx 覆盖、要么是占位串，**不是真 Key**。
- (2) 搜不到。
- (3) 只可能命中"渠道模板里的 baseUrl `/ziyu/api`"这类**非机密**字符串，**绝不能命中 Key**。

**证据**：三张截图 / 三段命令输出（**Key 一律打码或替换成 `sk-***`**）。

**不过怎么办**：**立即下线 `/ziyu/`**（nginx 注释掉 + reload），Key 视为已泄露、去紫域后台轮换。

> ★ 这一条是本计划**最硬的安全底线**（`ziyu.js` 第 8-11 行、紫域官方文档都写了 Key 只能放服务器）。

### A-07 · ★ 结果立即落盘，24 小时后仍可播放

**做什么**：任务完成后，**等 24 小时以上**（或等到紫域原 URL 失效），再从画布播放这条片子。

**期望**：**仍能播放**——因为已经落盘到 `MEDIA_ROOT`（`/opt/canvas-api-media`）。

**证据**：`media_files` 里该条记录的 `source_url`（原址）+ 本地 `storage_key`；播放截图。

**不过怎么办**：查 `persistRemoteMedia()` 是否被真的调用（`routes-credits.js` L281 `POST /api/ziyu/persist`）。**只写接口不调用 = 用户第二天丢片**。

**★ 落盘前置条件（第 20 轮新增，必查）**：`POST /api/ziyu/persist` 在调用 `persistRemoteMedia()` 之前**必须先走 `resolveResultUrls()`**（`ziyu.js`）：

1. 任务未 `completed` → 直接拒绝；
2. 任务 `completed` 但**取不到产出 URL** → **记 warning、返回失败、不落盘**（`RESULT_URL_MISSING`）；
3. **绝不能拿 `job.assets` 当产出**——实测 `job.assets` 是**输入参考素材**。

> 反例实证：任务 `195f4a3a` 结果 URL 已过 24 小时清理，`assets` 里只剩用户上传的 **5 张图 + 1 个视频**（`uploadedAt` 全部早于任务创建）。
> 若按旧结论遍历 `assets`，用户会拿到**自己上传的素材**当成品，且已扣点——比报错严重得多。

### A-07b · completed 但无产出 URL → 必须记 warning，不许标成功

**做什么**：取一条 `completed` 且结果 URL 已被紫域清理（超过 24 小时）的旧任务，走一遍落盘接口。

**证据**：接口响应 + 服务端日志 + `media_files` 前后行数。

### A-08 · 扣费以紫域 `cost` 为准（不是本地估算）

**做什么**：挑一个 `costPerSecond > 0` 的模型，跑一个较长时长的任务，比对三处数字：

1. 提交前预扣的点数
2. 紫域 job 返回的 `cost`
3. 本地 `credit_ledger` 里 `task_settlement` 的金额

**期望**：最终扣减 = `ceil(ziyuCost × 1.5)`，且 `ziyuCost` 来自**紫域返回**，不是本地 `costPerSecond × 秒数` 的估算。

**证据**：三处数字并列。

**不过怎么办**：查 `settleTaskCredits({ ziyuCost })` 的入参来源。

> ★ 已实测的坑：紫域 `models` 目录里的 `cost` **不等于真实扣费**。
> 实测 `zy_model_2db335ab16705b6ffb21` 提交 30 秒**实际扣 1500**，而目录里 `cost=200`、`costPerSecond=50`。
> 真实价 ≈ `costPerSecond × 秒数`。**所以只能以 job 返回的 `cost` 对账。**
> （证据：`_ziyuai_price30.txt` + `ziyuai-out\P1-job.json`，逐字复核。）

> 🟡 2026-09-13 追加（与 A-23 联动）：对账 SQL 里那条"应付点数"的表达式，本轮已与 `customerCost()` **逐值对齐**
> （18 个取值 0 处不匹配）。修之前 `cost = 0` 的失败任务会被 SQL 判成"应付 1 点"而误报差异。
> 见 `docs/VERIFICATION_20260913_BILLING.md` §七之三（缺陷 A）。

### A-09 · 失败任务按紫域 `cost` 处置，不假设必退

**做什么**：故意跑一个会失败的任务（比如用不被支持的模式）。

**期望**：

- 紫域返回 `failed` 时，读 `cost`：
  - `cost = 0` → **不退**（本来就没扣）。
  - `cost > 0` → 按既定规则处置（记流水 + 落 `channel_usage`），**不是自动全退**。
- 本地不出现"用户余额凭空多回来"的情况。

**证据**：失败任务的 job 返回 + 本地流水。

**不过怎么办**：查是否有"失败即退款"的想当然代码。

> ★ 实测：失败任务**有记 200 积分的，也有记 0 的**。紫域官方文档说"失败会返还"，
> **与实测不符**。以实测为准。

> 🟡 2026-09-13 追加：`cost = 0` 的失败任务**也要在 `channel_usage` 里留一行** —— 否则它从对账里彻底消失。
> 本轮已补：预扣（含零预扣）、结算、退款三个分支都会写 `channel_usage`。

### A-10A · ★ 并发预扣只扣一次（同一 taskId）

**做什么**：对**同一个 taskId** 并发发起 3 次预扣。

**期望**：**只有 1 次真正扣款**，另外 2 次返回 `duplicate: true`；
余额只减一次；`credit_ledger` 里 `reason='task_reservation'` 的流水**只有 1 条**。

**证据**：3 次返回的 JSON + 余额 + 流水条数。

**★ 这一项不是"顺带检查"**：本仓桩环境实测，**修复前**存在真实的并发重复扣费漏洞
（先 `SELECT` 再 `UPDATE` 只能防顺序重复，防不住并发）。修复方式是 `credits.js` 的
`lockTask()`（L142-144）用 `pg_advisory_xact_lock(hashtext('canvas-task:' || task_id))` 加锁。

**不过怎么办**：确认 `reserveTaskCredits`（L154-194）里 L162 的加锁调用还在，
以及 L171 的幂等短路、L176 的条件扣减（`WHERE balance >= $2`）都没被改掉。

---

### A-10B · ★ 并发结算只结一次，且已结算任务拒绝退款

**做什么**：两小步——(1) 对同一 taskId 并发发起 2 次结算；(2) 结算完成后再调一次退款。

**期望**：

- (1) 第一次返回正常（`delta` 按紫域 `cost` 算），第二次返回 `duplicate: true`，余额只动一次；
- (2) 返回 `{ ok: false, code: "ALREADY_SETTLED" }`，**HTTP 409**，余额**不变**。

**★ 这一项同样不是"顺带检查"**：本仓桩环境实测，**修复前**已结算任务可以再次退款，
返回 `{ok:true, refunded:true, amount:300}` —— 也就是**平台白送钱**。
修复方式是 `refundTaskCredits()`（L285-336）L288 加锁 + L294-300 的 `ALREADY_SETTLED` 前置检查，
路由层对应 `routes-credits.js` **L208-219** 的 409 分支。

**证据**：两次结算返回 + 退款返回 + 余额前后对比。

**不过怎么办**：查 L294-300 的前置检查是否被绕过（比如在事务外先查状态）。

### A-13 · 注册开关收口 + 新用户拿不到管理员

> ⚠️ **2026-09-13 线上实测订正**：`CANVAS_ALLOW_REGISTER` 线上**当前是【开】的**（证据：`POST /api/auth/register` 返回
> 400 `password_too_short` 而不是 403 `registration_closed`，且该请求未创建账号）。
> 所以 A-13 的第一步不是「打开注册」，而是**先把它关掉**。完整证据链见
> `implementation/deploy/batch2-acceptance.md` §0.1 与 `docs/STATUS_20260913_LIVE_GATE.md`。

**做什么（按此顺序）**：

1. ★ **先收口**：服务器 `.env` 加 `CANVAS_ALLOW_REGISTER=0` → **重建 api 容器**（不重建不生效）。
2. 查 `users` 表：确认**你本人 `role = 'admin'`**，且没有陌生账号（首个注册者会被 `promoteToAdminIfFirst()` 提为管理员）。
3. 批次 1 落地：额度体系对**所有** `/ziyu/` 调用生效（`requireAuth` + 余额预扣）。
4. 收紧 `/api/auth/verify` 的 legacy 分支（`server.js` L89-96 同时接受真会话或 legacy cookie）。
5. **最后**才把 `CANVAS_ALLOW_REGISTER` 设回 `1`（重新放开公开注册），并用一个新邮箱注册。

**期望**：新用户 `role = 'user'`；访问 `/api/admin/credits/overview` 返回 **403**。

**证据**：两个账号的 role + 403 返回。

**不过怎么办**：查 `promoteToAdminIfFirst()`（`auth.js` L118）是否只对第一个注册者生效；
查 `requireAdmin` 中间件是否真的挂在管理员路由上（`routes-credits.js` L339-389）。

> ★ **顺序不能反**：**先收口注册开关 → 再确认你是管理员 → 再上额度体系 → 最后才放开注册**。
> 反了的话：第一个注册的陌生人会变成管理员（`count(*) <= 1` → `role=admin`），
> 而且他注册成功就顺带拿到门禁 cookie（B-6），能直接调 `/ziyu/` 花掉服务器上的紫域额度。

### D-web-1 · 渠道模板的 `apiKey` 怎么办

**冲突事实**（两边都有行号证据）：

- `web/src/services/api/video.ts` **L83-85**：插件路径要求 `baseUrl` 与 `apiKey` **都非空**才放行；
  **L191-196** `assertVideoConfig` 同样卡 `apiKey`。
- `web/src/stores/channel-templates.ts` **L65-76** `createChannelFromTemplate()` **写死 `apiKey: ""`**。
- 而 `ChannelTemplate` 类型（`web/src/stores/channel-templates.ts` **L9-20**，共 7 个字段）
  **根本没有 `script` / `apiKey` 字段**。
- 但模型级类型 `ChannelModel.script?: string` **已经存在**（`web/src/stores/use-config-store.ts` **L16**，已复核）。
  也就是说：**类型层面不需要动，缺的只是"模板把 script 透传下去"**。

**后果**：按现状，紫域视频渠道**一定提交不出去**（空 key 直接抛错）。

**三个方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **(a) 推荐** | 模板填非密钥占位串 `ziyu-proxy`（**已按此写在 `ziyu-channel-template.json`**） | 需改 `createChannelFromTemplate` 或让用户手填；占位串会进构建产物，但**不是机密** |
| (b) | 改 `createChannelFromTemplate()` 允许"无需 key" | 动的是**通用函数**，影响 openlux / omniroute / midjourney 三条现有模板 |
| (c) | 改 `video.ts` 的检查（允许空 key + 插件脚本） | 动的是**核心链路**，风险最大 |

**为什么推荐 (a)**：唯一一个"只动新代码、不动现有模板与核心链路"的方案。
安全性不受影响 —— nginx 会用 `proxy_set_header` **覆盖**浏览器发来的 `Authorization`，
前端填什么都不会影响真实 Key。

> ⚠️ 另有一个连带问题：`ziyu.js` L16-18 的注释写"前端模板里的 apiKey 保持空字符串
> （createChannelFromTemplate 的铁律）"，**与 `video.ts` L85/L194 硬冲突**。
> 无论选哪个方案，**这段注释都要改**，否则下一轮审计会被它误导。

### D-batch2-ziyu-gate · 批次 2 撤门禁时的资金敞口

**事实链**：

1. `canvas-api/server.js` **L89-96** 的 `/api/auth/verify` 同时接受
   **真会话（`canvas_session` JWT）** **或** **legacy 站点 cookie**（`CANVAS_LEGACY_TOKEN`）。
2. 批次 2 的目标是撤掉 `/`、`/assets/`、`/config.js`、`/agnes/` 四处门禁。
3. 撤掉之后，**任何曾经拿到过旧站点密码的人**，只要手里留着那枚 `canvas_auth` cookie，
   就仍能通过 `verify` → 进而调用 `/ziyu/` 花掉**服务器上的紫域额度** ——
   而他可能没有本站账号、也没有余额。

**这是一个"先花钱后记账"的敞口。**

> ★ **B-6 扩面（2026-09-13 线上实测）**：上面第 3 条只覆盖了「曾经拿到过站点密码的人」。
> 实测发现敞口更大：**注册接口是开的**，而注册/登录成功时服务端会**自动下发** `canvas_auth` 门禁 cookie
> （`auth.js` `setSessionCookies()` → `setSitePassCookie()`）。
> ⇒ 任何知道注册接口的人，**注册一次就拿到门禁 cookie**，无需知道站点密码。
> **站点密码对这类人是透明的**；唯一挡得住的是额度体系（`requireAuth` + 余额预扣）。
> 证据链见 `implementation/deploy/batch2-acceptance.md` §0.1。

**正确顺序**（三者颠倒任一种 = 给陌生人开免费出片机）：

1. 先让额度体系对**所有** `/ziyu/` 调用生效（预扣 + 结算）。
2. 再把 `/api/auth/verify` 的 legacy 分支收紧为只读 / 或直接下线。
3. 最后才考虑撤 `/ziyu/` 门禁。

**需要用户裁决**：

- 是否同意 `/ziyu/` 在批次 2 **保留门禁**（不与其他四处一起撤）？
- 是否接受"持旧站点 cookie 者仍可烧积分"这段过渡期？如果不接受，legacy 分支什么时候收紧？
