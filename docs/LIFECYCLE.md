# 生命周期 · 无限画布（hb.cauai.fun）

> **本文件解决「现在是规则集合，不是可执行生命周期」的问题。**
> 九阶段 + 六闸门。**每个阶段必须有可验证的退出条件**——决定产品有没有短板的，不是流程有多全，
> 而是每个阶段有没有一个明确的"不许过去"的门槛。
> 版本：v1.0 · 2026-09-17

---

## 0. 状态机

```text
需求 → 规格 → 约束 → 计划 → 实现 → 测试 → 审查 → 发布 → 复盘
  G1      G2     (随G2)  G3      G4      G5      G6      →回到需求
```

**两条硬规则**：

1. **不许跳阶段。** 但 L0 级变更可走快速通道（见 `CHANGE-RISK.md`）。
2. **闸门不过 = 停在原地，不许"先做着再说"。** 历史上「批次 1 已完成」的错误标注，
   本质就是跳过了 G4（验证）直接宣布完成。

## 1. 九阶段定义

### 阶段 1 · 需求（Requirement）

| 项 | 内容 |
|---|---|
| **输入** | 一个模糊的想法、一个报障、一个机会 |
| **产物** | Problem Brief：用户是谁 / 要解决什么 / 不做什么 / 为什么现在做 |
| **退出条件** | 能答出 `PRODUCT_CHARTER.md` 的「用户必答五问」；答不上来的需求**不进路线图** |
| **负责人** | 提出者 + 项目 owner |
| **闸门** | **G1**：owner 明确批准 |

### 阶段 2 · 规格（Spec）

| 项 | 内容 |
|---|---|
| **输入** | 已批准的 Problem Brief |
| **产物** | 可测试的验收标准（追加进 `implementation/deploy/ACCEPTANCE.md`，编号不复用） |
| **退出条件** | 每条验收标准都能被**一条命令或一次点击**判定通过/失败；含主流程**与失败流程** |
| **负责人** | 提出者 |
| **闸门** | **G2**：验收标准可测试 |

### 阶段 3 · 约束（Constraints）

| 项 | 内容 |
|---|---|
| **输入** | 已批准的规格 |
| **产物** | 本次变更触及的约束清单（引用 `CONSTRAINTS.md` 的 C 编号 + `AGENTS.md` 的领域条款） |
| **退出条件** | 明确写出：安全、数据来源、架构边界、性能、是否触及不可再生数据 |
| **负责人** | 实现者 |
| **闸门** | 随 G2 一起过（不单独设闸，避免流程过重） |

### 阶段 4 · 计划（Plan）

| 项 | 内容 |
|---|---|
| **输入** | 规格 + 约束 |
| **产物** | 任务清单（写进 `docs/BACKLOG.md`；跨批次范围写进 `docs/ROADMAP.md`） |
| **退出条件** | 每个任务：≤5 个文件 / 有独立验证命令 / 不与其他任务共享未提交状态 / **标注 L0–L3 风险级** |
| **负责人** | 实现者 |
| **闸门** | —（计划本身不设闸，由 G3 兜住） |

### 阶段 5 · 实现（Implementation）

| 项 | 内容 |
|---|---|
| **输入** | 已批准的任务 |
| **产物** | 代码 + 测试（先写失败测试，再写最小实现） |
| **退出条件** | 每个切片独立可验证；原子提交；Conventional Commits |
| **负责人** | 实现者 |
| **闸门** | **★ G3：落地闸门（本次新增，见 §2）** |

### 阶段 6 · 测试（Test）

| 项 | 内容 |
|---|---|
| **输入** | 实现完成的代码 |
| **产物** | 测试与验证记录（追加 `docs/STATUS_YYYYMMDD_*.md`） |
| **退出条件** | 核心流程 + **错误路径**都跑过；**断言结果落盘**（不能只 `console.log`）；`verify.mjs` 退出码 0 |
| **负责人** | 实现者 |
| **闸门** | **G4**：验证通过 |

### 阶段 7 · 审查（Review）

| 项 | 内容 |
|---|---|
| **输入** | 变更 + 测试记录 |
| **产物** | Review Report，按 `[blocking]` / `[important]` / `[nit]` / `[praise]` 分级 |
| **退出条件** | **blocking = 0**；每条问题含「文件位置 / 问题 / 为什么重要 / 怎么修」 |
| **负责人** | 独立 reviewer（L3 变更需双人） |
| **闸门** | **G5**：审查通过 |

### 阶段 8 · 发布（Ship）

| 项 | 内容 |
|---|---|
| **输入** | 通过审查的变更 |
| **产物** | 发布记录 + 发布后验证证据 |
| **退出条件** | 回滚方案已验证 / 版本指纹可区分新旧 / 不可再生数据卷已确认 / 发布后冒烟通过 |
| **负责人** | 发布者 |
| **闸门** | **★ G6：发布闸门** |

### 阶段 9 · 复盘（Retro）

| 项 | 内容 |
|---|---|
| **输入** | 一次发布或一次事故 |
| **产物** | `docs/STATUS_YYYYMMDD_*.md`（**只追加，不改结论**） |
| **退出条件** | 至少写出：做对了什么 / 做错了什么 / 哪条约束被违反 / 下次怎么更早发现 |
| **负责人** | 参与者 |
| **闸门** | —（产出回流到阶段 1） |

## 2. ★ 闸门 G3：落地闸门（本次新增，最重要的一条）

### 为什么现在必须有

既有文档记录「写权威源码树返回 `EPERM`」（D10.9 B-2），把落代码当成**技术阻塞**。
**2026-09-17 实测：权威源码树可写**（`PROJECT_CONTEXT.md` §4）。

这意味着：

- 「批次 1 未落地」**不再是环境问题，是决策问题**；
- 同时也意味着**任何一次误执行都会真的改动权威树**；
- 而权威树连着 `AUTH_COOKIE`、三个不可再生数据卷和真金白银的额度。

**所以必须有一个显式的、书面的人为闸门，而不是靠"没人反对"。**

### G3 的通过条件（四条全满足）

| # | 条件 | 检查方式 |
|---|---|---|
| G3-a | 本次落地范围已用**零写入干跑**验证过锚点 | `node implementation/scripts/dry-run-all.mjs` 退出码 0 |
| G3-b | 落地影响到的**不可再生数据卷**已逐一确认（或确认不涉及） | 对照 `AGENTS.md` §5 四个卷 |
| G3-c | **回滚方案已存在且被读过**（不是"应该能回滚"） | 指向 `implementation/deploy/ROLLBACK.md` 的具体条目 |
| G3-d | **owner 明确书面批准**（在本次任务里说出"批准落地"） | 对话记录；不得由 AI 代为推定 |

**G3-d 是唯一不可绕过的一条。** 即使 a/b/c 全绿，没有 d 也不许写权威树。

### G3 的例外

- 治理仓（`E:\codex\huabu`）内的文档与脚本改动**不需要 G3**。
- 零写入干跑（`dry-run-all.mjs`）**不需要 G3**（它不写盘，这是它被设计成默认验证手段的原因）。

## 3. 闸门总表

| 闸门 | 阶段 | 一句话 | 本项目的现成判据 |
|---|---|---|---|
| **G1** | 需求 | owner 批准 | `PRODUCT_CHARTER.md` 五问答得出来 |

| **G4** | 测试 | 验证通过且断言落盘 | `verify.mjs` 0 + `STATUS_YYYYMMDD_*.md` |
| **G5** | 审查 | blocking = 0 | Review Report |
| **G6** | 发布 | 可回滚 + 版本可验 + 冒烟通过 | 主 JS 指纹 + 上线自检 10 项 |
