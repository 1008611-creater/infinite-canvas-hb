# 架构重置基线 · 无限画布

> 状态：已批准并执行中（2026-09-21）。本文件定义治理架构；权威源码只按已批准垂直切片增量修改，尚未重新发布。
> 目的：把“做功能”改成可审计的交付生命周期，停止继续在现有实现上无闸门叠加功能。

## 结论

当前项目的问题不是缺少更多功能，而是“规格、约束、实现、验收、发布”没有形成强制的状态机。之前的工作容易在上游合并、批次落地和临时修复之间来回跳转，导致结果能运行但不可证明、不可稳定回滚、不可复用。

从本文件生效起，每个变更必须走：

```text
DEFINE → SPEC → CONSTRAIN → PLAN → BUILD → VERIFY → REVIEW → SHIP → RETRO
```

任何阶段没有产物或退出条件，不能进入下一阶段。架构图见 [architecture-reset.html](architecture-reset.html)，可编辑规格见 [architecture-reset.architecture.json](architecture-reset.architecture.json)。

## 分层与依赖方向

权威源码不是 Next.js 项目，因此不照搬 `app / components / lib` 目录名，而按真实边界约束依赖：

```text
web（交互与编排）
  → web/src/services/api（协议适配）
  → canvas-api / agnes-video-proxy / canvas-webdav（服务边界）
  → Postgres / 持久化卷（数据所有权）

web 不直接持有服务器密钥；
canvas-api 不依赖 React/UI；
代理不决定产品验收；
deploy 只负责运行时组合，不承载业务规则。
```

跨层调用必须有明确的接口契约、错误语义和测试；禁止把业务判断塞进 nginx 片段、落地脚本或一次性发布命令。

## 每次变更的标准产物

1. **Problem Brief**：目标用户、问题、非目标、范围、owner。
2. **Spec**：主流程、失败流程、可测验收标准、数据与凭证边界。
3. **Constraint Record**：引用 `AGENTS.md` / `CONSTRAINTS.md` 条款，并标注 L0–L3 风险级别。
4. **Implementation Plan**：按垂直切片拆分，每项不超过 5 个文件，写清输入、输出、验证命令和依赖。
5. **Build Record**：代码、测试、变更摘要；先写失败测试，再写最小实现。
6. **Verification Record**：类型检查、单测、契约/API、真实浏览器主流程与错误路径、密钥扫描、构建和冒烟。
7. **Review Report**：按 `[blocking] / [important] / [nit] / [praise]` 分级，blocking 必须为 0。
8. **Release Record**：版本指纹、回滚命令、发布后验证、不可再生数据确认。
9. **Retro**：做对什么、做错什么、哪条闸门失效、下次如何提前发现。

## 与当前项目的直接差距

- `docs/PROJECT_CONTEXT.md` 已完成审计，但它明确记录“缺少可执行生命周期”；这正是本次重构入口。
- `docs/LIFECYCLE.md` 已有 G1–G6，但之前更像规则集；需要把每个阶段的产物绑定到实际任务，而不是只在文档里描述。
- `scripts/verify.mjs` 当前能证明治理仓链接、敏感串、口径和干跑一致；它不能证明权威源码的功能质量，也不能替代真实浏览器/API 验收。
- 现有批次文档把设计、落地、线上状态混在时间轴里；重构期间先冻结新增批次，先补齐规格、实现计划和验证证据。

## 重构顺序

1. **冻结**：不新增功能、不继续上游合并、不做未经批准的权威源码改动。
2. **定义**：为当前最重要的一条用户价值链写 Problem Brief 和 Spec；先选一条垂直切片，不重写全站。
3. **约束**：逐条绑定凭证、不可再生数据、额度扣费、部署回滚和依赖方向；L2/L3 变更必须有回滚方案。
4. **计划**：生成一份可执行计划，任务之间不得共享未提交状态；明确每项的失败测试和验证命令。
5. **增量实现**：每次只交付一个垂直切片；不接受“顺手修一批”的隐性范围扩张。
6. **证据验收**：主流程、错误流程和真实边界分别验证，结果落盘；没有证据就标记 `unverified`。
7. **独立审查**：先功能正确性，再架构/安全/性能/可维护性，最后检查测试完整性。
8. **发布与复盘**：通过 G6 后才发布；发布后记录版本指纹和回滚演练结果，再把缺口回流 ROADMAP。

## 不允许的做法

- 先写代码、后补需求和验收。
- 把 `verify.mjs` 通过当成产品已验收。
- 用 mock、占位日志或“接口返回 200”替代真实用户流程证据。
- 把“节点连上了”写成“节点链已真实执行”。
- 把一次成功发布写成“可回滚”，但没有实际回滚路径和版本指纹。
- 在没有 G3 书面批准时改权威源码树、服务器配置或不可再生数据。
