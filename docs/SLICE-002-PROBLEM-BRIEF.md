# 垂直切片 002 · Problem Brief

> 状态：owner 已于 2026-09-21 定下方向（「一个入口 + 一套账号 + 一套额度，三个产品各留各的数据」）。
> 本文件把这个方向固化成可审批的范围。**尚未进入实现，尚未改动权威源码树。**

## 问题

`hb.cauai.fun`（无限画布）、`sd2.cauai.fun`（念念 AI 视频工作台）、`apic.cauai.fun`（New API 网关）由同一个所有者部署在同一台服务器上，但三个产品互相不知道对方存在：

- 用户要在三个站点各注册一次、各记一套密码。
- 三套额度互不相通，用户不知道自己「总共还剩多少」。
- 同一个人的消耗分散在三本账上，既无法对账，也无法按人做风控。

结果是三个产品看起来像三个互不相关的小站，而不是一个可信的产品矩阵。对用户的直接代价是重复注册、钱散在三个地方；对平台的直接代价是无法回答「这个人一共花了多少、还剩多少」。

## 目标用户

已经在 `cauai.fun` 名下使用 AI 视频 / 图片能力的创作者，以及内部使用者。第一刀只覆盖「同一个自然人跨站点使用」这一件事，不代表三个产品的业务数据要合并。

## 本次目标

在不合并三站业务数据的前提下，让一个账号能：

1. 从一个统一入口进入，并选择要去的产品。
2. 只登录一次，进入任一产品都不需要再输密码。
3. 看到一份统一的可用额度，且在任一产品里的消耗都从这唯一一份额度里扣。
4. 在任一产品里查看自己的消耗明细，明细能追到具体任务。

## 明确不做

- **不合并三站的业务数据**：画布数据库、sd2 业务库、媒体库、云同步卷仍各自独立（延续 D22 与 `AGENTS.md` §5）。
- 不改 `AUTH_COOKIE` 与 `CANVAS_LEGACY_TOKEN`（`AGENTS.md` §2 红线）。
- 不动四个不可再生数据卷（`AGENTS.md` §5）。
- 不做跨产品的历史数据迁移，不做老账号的批量合并。
- 不在本切片新增或重构任一产品的业务功能。
- 不把「三站互相加了链接」当成「已经统一」。
- 不把任一产品的界面重新设计一遍。

## 为什么现在做

`implementation/NEW-API-APIC-READINESS-20260918.md` §4 P4 已经写下授权入口：

> 先让画布作为 New API 客户端使用，不合并两个账本。统一账号和统一余额另立规格，经过并发扣费与退款测试后再决定。

本切片就是那句「另立规格」的产物。它不是新开的野心，而是既有路线上已经挂账的一步。

## Owner 与闸门

- Owner：项目 owner。
- **G1**：确认本范围与「明确不做」。
- **G2**：验收标准见 `docs/SLICE-002-SPEC.md`，每条都要能被一条命令或一次点击判定。
- **G3**：本切片是 **L3**（改鉴权 + 改资金路径 + 改部署路由），必须 owner 书面批准；统一入口、统一账号、统一额度三项各自还需要独立的落地批准。
- **G4 / G5 / G6**：按 `docs/LIFECYCLE.md`，L3 需两名 reviewer、零写入干跑、回滚方案和发布后冒烟。

## 风险预告（不写清楚就会变成后面的返工）

1. 三套密码哈希算法互不兼容（bcryptjs / scrypt + 独立盐列 / Go 自有），统一账号必须显式选择迁移方式，不能直接搬哈希。
2. New API 的 OIDC 是**客户端**不是身份提供方，统一账号的技术形态没有现成答案，需要 owner 在候选方案里裁决。
3. 统一额度会同时改动 hb 与 sd2 的扣费路径，而 sd2 有「下单即预扣、终态结算、失败退款」的硬规则，并发与退款必须单独验证。
4. `apic.cauai.fun` 的公开注册当前仍开启（D22 执行订正）。一旦它成为账号权威，这个开关就直接变成三个产品共同的注册开关。

以上四条在 `docs/SLICE-002-SPEC.md` 里逐条处理。
