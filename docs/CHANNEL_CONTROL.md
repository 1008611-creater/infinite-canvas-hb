# 渠道控制设计与准备清单

> 版本：v1.0 · 2026-09-18
> 状态：设计与准备阶段，尚未改权威源码，尚未发布线上。
>
> 本文件解决的问题：让网站方能够明确控制平台渠道的启停、模型范围、权限、成本、额度、审计和回滚，同时保留用户自带渠道的自由度。

## 1. 结论先行

当前渠道配置主要保存在浏览器 localStorage：`infinite-canvas:ai_config_store`。用户可以新增、编辑、删除渠道，修改 `baseUrl`、API Key、模型和模型脚本。

这套设计适合“用户自带渠道”（BYO），不适合直接作为平台托管渠道的控制面。紫域、Agnes 等由平台承担成本或持有服务端凭据的渠道，必须与 BYO 渠道分离。

目标模型：

```text
平台托管渠道（Platform-managed）
  服务端登记 → 管理员控制 → 模型白名单 → 权限/限流 → 额度/成本 → 审计/回滚

用户自带渠道（BYO）
  浏览器本地保存 → 用户自己提供凭据 → 平台不代理、不计费、不托管
```

## 2. 当前事实

| 项目 | 当前状态 | 证据/位置 | 风险 |
|---|---|---|---|
| 渠道存储 | Zustand persist，浏览器 localStorage | `web/src/stores/use-config-store.ts` 的 `CONFIG_STORE_KEY` | 多个浏览器之间不一致，平台无法统一收口 |
| 渠道编辑 | 可新增、编辑、删除 | `web/src/components/layout/app-config-modal.tsx`、`channel-editor-drawer.tsx` | 普通用户可以修改所有渠道字段 |
| API Key | 统一作为 `ModelChannel.apiKey` 前端字段 | `web/src/stores/use-config-store.ts` | 平台凭据与用户凭据语义混杂 |
| 模型列表 | 可由前端编辑；模型脚本也可编辑 | `channel-editor-drawer.tsx` | 平台渠道可能被追加未审核模型或改写请求逻辑 |
| Agnes | 通过 `/agnes` 代理和服务端环境变量控制 | `deploy/nginx-docker.conf`、`constant/env.ts` | 有固定代理控制，但缺统一渠道状态模型 |
| 紫域 | `/ziyu/` 服务端反代，Key 由服务端注入；脚本内嵌额度事务 | `deploy/nginx-docker.conf`、`channel-templates.ts` | 平台渠道仍以普通前端 ModelChannel 形式出现 |
| 额度 | 紫域脚本提交前 reserve、终态 settle、提交失败 refund | `channel-templates.ts`、`canvas-api/credits.js` | 需要把 channelId/modelId/政策版本固定写入审计 |
| 管理入口 | 有额度/兑换相关管理员接口 | `canvas-api/routes-credits.js` | 尚无统一渠道注册、启停、版本、审计接口 |

## 3. 不可违反的边界

### 3.1 平台渠道

平台渠道包括但不限于紫域、Agnes，以及未来由网站方持有凭据或承担上游成本的渠道。

必须满足：

- 真实凭据只存在服务器秘密配置，不进仓库、前端 bundle、localStorage、导出文件和普通日志；
- 普通用户不能修改 `baseUrl`、凭据、模型脚本和平台模型白名单；
- 每次调用必须绑定 `channelId`、`modelId`、配置版本、计费政策版本和用户身份；
- 渠道或模型停用后，新的任务必须 fail-closed，不得静默切换到其他收费渠道；
- 变更前必须有版本、审计记录和回滚目标；
- 额度预扣、上游实际成本、结算、退款和结果落盘必须能按任务关联。

### 3.2 用户自带渠道

BYO 渠道可以保留浏览器本地配置，但必须明确：

- 凭据只存浏览器本地，不同步到服务端；
- 平台不做代理转发，不持有用户凭据；
- 不进入平台额度和平台成本对账；
- 页面显示“用户自带渠道”，不能伪装成平台官方渠道；
- 用户自行承担上游费用、配额、可用性和凭据安全；
- 导出配置前必须提示其中可能含用户自己的凭据。

## 4. 目标控制模型

### 4.1 平台渠道注册表

建议新增服务端渠道注册表，最小字段：

```text
id
provider
name
ownership              platform | byo
credential_mode        server | browser
billing_mode           free | platform_credits | byo
status                 active | paused | disabled | degraded
visibility              public | admin | private
capabilities            image/video/text/audio
allowed_models         模型白名单或引用
rate_policy_id         限流策略
cost_policy_id         成本/扣点策略
config_version
policy_version
created_at
updated_at
updated_by
```

注意：表中不存真实 API Key。凭据仍由服务器秘密管理系统或 `.env` 管理；数据库只保存 `credential_ref` 或安全指纹。

### 4.2 模型白名单

上游实时目录与网站允许目录必须分离：

```text
上游目录：用于发现可用模型
网站白名单：由管理员批准后对外展示
```

模型最小字段：

```text
model_id
channel_id
capability
status
public_name
provider_model_id
billing_policy_id
max_duration
max_resolution
allowed_modes
config_version
```

上游新增模型不得自动对普通用户开放；上游下架模型不得静默替换成其他模型。

### 4.3 权限矩阵

| 操作 | 普通用户 | 管理员 | 服务端运维 |
|---|---:|---:|---:|
| 使用已开放平台渠道 | 允许 | 允许 | 不适用 |
| 使用已开放模型 | 允许 | 允许 | 不适用 |
| 新增 BYO 渠道 | 允许，本地 | 允许，本地 | 不适用 |
| 修改平台渠道地址/凭据 | 禁止 | 受审计控制 | 受发布闸门控制 |
| 修改平台模型白名单 | 禁止 | 允许，需版本 | 允许发布 |
| 启停平台渠道 | 禁止 | 允许，需二次确认 | 可执行应急操作 |
| 修改扣点策略 | 禁止 | 禁止直接改生产值 | 需单独批准和发布 |
| 查看明文凭据 | 禁止 | 禁止 | 原则上也禁止回显 |
| 查看调用/失败/成本摘要 | 仅本人 | 全局 | 全局 |
| 回滚渠道配置 | 禁止 | 允许选择版本 | 负责执行发布/重建 |

## 5. 必须准备的控制能力

### P0：先做，才能称为“可控”

1. **渠道身份分离**：平台渠道与 BYO 渠道不能共用同一套可编辑语义。
2. **平台渠道只读前端**：普通用户不能改平台渠道的 URL、Key、模型和脚本。
3. **平台模型白名单**：上游目录不等于网站开放目录。
4. **启停 fail-closed**：暂停渠道后新任务拒绝，不能自动切换并继续烧另一套额度。
5. **任务绑定控制信息**：保存 `channelId`、`modelId`、配置版本、政策版本、用户 ID。
6. **平台凭据隔离**：前端、localStorage、导出文件、日志和错误消息都不能出现真实平台 Key。
7. **紧急停用**：管理员可单独停渠道、停模型，不需要改前端代码。

### P1：上线运营前准备

1. 渠道健康检查：模型目录、鉴权、上游响应时间、429/5xx、最近成功时间。
2. 渠道级限流：全局、用户、模型、并发和每日预算。
3. 成本保护：单任务最大预扣、最大时长、最大分辨率、每日总预算。
4. 审计日志：谁在什么时候做了什么变更，保留前后版本，不记录明文 Key。
5. 配置版本与回滚：每次发布可定位版本，失败时能恢复上一版本。
6. 故障状态：`active`、`paused`、`degraded`、`disabled` 不能只存在内存。
7. 对账看板：上游实际成本、平台扣点、退款、未结算和结果落盘状态。

### P2：规模化前准备

1. 渠道分组与路由策略；
2. 备用渠道必须显式批准，禁止静默 fallback；
3. 模型价格变更的生效时间和存量任务口径；
4. 配额异常告警；
5. 管理员双人复核或高风险操作二次确认；
6. 配置导入导出脱敏；
7. 渠道插件脚本签名或改为服务端固定脚本。

## 6. 推荐实施顺序

### 阶段 A：不改线上，先完成规格

产物：本文件 + 决策记录 + 验收项。

必须裁决：

- 平台渠道是否允许管理员在网页改配置，还是只允许改配置文件后发布；
- BYO 渠道是否继续支持导出；
- 平台模型是否全部走白名单；
- 渠道暂停时是否允许管理员测试；
- 预算单位采用上游积分、本站点数还是人民币；
- 是否允许显式备用渠道。

### 阶段 B：前端先收边界

只改权威源码的前端：

- 标记平台渠道 / BYO 渠道；
- 平台渠道只读；
- 隐藏平台 Key，不回填明文；
- 平台模型禁止新增、删除和脚本编辑；
- BYO 渠道保留本地编辑能力；
- 保存前显示渠道归属和凭据存储位置。

### 阶段 C：服务端建立控制面

新增服务端渠道注册、状态、模型白名单、权限、审计和版本接口；前端读取平台渠道时以服务端为准。

### 阶段 D：接入预算与运营

把渠道控制信息接入任务、额度、限流、健康检查、告警和对账，再考虑开放更多平台渠道。

## 7. 验收标准草案

- [ ] 普通用户无法修改平台渠道 `baseUrl`、模型列表、脚本和凭据。
- [ ] 普通用户可以新增和编辑 BYO 渠道，且凭据不上传服务端。
- [ ] 平台 Key 在 bundle、localStorage、导出 JSON、接口响应和日志中均无明文。
- [ ] 管理员暂停渠道后，新任务明确拒绝，且不发生上游调用。
- [ ] 禁用单个模型后，新任务明确拒绝，且不自动切换模型。
- [ ] 上游目录新增模型不会自动向普通用户开放。
- [ ] 每个任务记录渠道、模型、配置版本和计费政策版本。
- [ ] 渠道配置变更可查询操作者、时间、前后版本和回滚目标。
- [ ] 回滚后新任务使用旧版本，存量任务不被重写。
- [ ] 发生上游 401/429/5xx 时，状态和审计记录可见，且不会静默烧备用渠道额度。
- [ ] 渠道健康检查不创建真实任务、不消耗上游额度。

## 8. 本阶段不做

- 不更换紫域唯一 Key；
- 不改变线上渠道状态；
- 不将真实 Key 写入治理仓；
- 不默认新增收费渠道；
- 不把 BYO 渠道凭据迁移到服务端；
- 不在没有验收标准和回滚方案时直接改权威源码。
